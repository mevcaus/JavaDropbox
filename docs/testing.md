# Testing

The backend uses **JUnit 5** with **Spring Boot Test** and **MockMvc** for integration testing. Every test that uses a database runs against **PostgreSQL 15 via Testcontainers**, on the schema the Flyway migrations build, the S3 storage tests run against **[S3Mock](https://github.com/adobe/S3Mock) via Testcontainers**, and the Elasticsearch search tests against **Elasticsearch 8.18 via Testcontainers** (a large image, pulled once), so Docker must be running.

```bash
# Run all backend tests
./gradlew test

# The tests, the coverage report and its minimums, and the format check
./gradlew check
```

### Backend coverage minimums

`./gradlew check` (and so `./gradlew build`) measures the backend's coverage with **JaCoCo** and writes the report to `build/reports/jacoco/test/html/index.html`, with an XML copy beside it. It fails when the tests cover less than 91% of lines or 82% of branches, the minimums in `build.gradle`'s `jacocoTestCoverageVerification`. They sit just under the coverage when they were set (91.6% and 83.0%), which leaves about 20 lines and 14 branches of slack: coverage can't fall by more than about half a point, though a small untested change can use up the slack and leave the failure to the next one. Raise them when coverage rises; lower them only on purpose, in a change that says why. In CI the `build` job puts the totals in its job summary and uploads the report as the `backend-coverage` artifact, failed minimums included, and on `main` the README's backend coverage badge is updated from it.

### Test Design Highlights
- **The production schema everywhere**: One PostgreSQL 15 container serves the whole run, and each Spring context gets an empty database of its own in it, which Flyway migrates and Hibernate validates with the production settings (`TestDatabaseEnvironment`, registered in `src/test/resources/META-INF/spring.factories`). Every test sees the real constraints, partial unique indexes and cascades, and the migrations run on every build
- **Production's settings**: Tests run on `src/main/resources/application.properties` as it is. Their own settings in `src/test/resources/config/application.properties` only add to it, so a test that depends on a production setting (forwarded headers, upload limits, what Actuator exposes, the API docs being off) runs with the value a real install has
- **Test isolation**: Contexts never share a database, so nothing one leaves behind reaches another, even from work done outside a test (startup, the search index's background thread). Test classes with the same configuration share one context and its database, so each wipes every table after a test through `TestDatabase.wipe`. The suites that change files first check, through `TestDatabase.assertUsageMatchesRows`, that each account's running total of what it stores matches what its rows add up to, so a change that forgets to count its bytes fails there. A class marked `@TempServingDirectory` also gets a context of its own on an empty temporary serving directory, which `TestStorage.empty` clears between tests
- **Databases in another state**: The migration and upgrade tests take a database of their own from the shared container, migrate it to an older schema or build a pre-Flyway one, and point their context at it, all through `PostgresTestSupport`

cd frontend
npm test

# The same, with the coverage report and its thresholds, as CI runs it

#### Frontend coverage thresholds

`npm test -- --coverage` measures the frontend's coverage with **`@vitest/coverage-v8`** and writes the report to `frontend/coverage/index.html`, with an `lcov.info` copy beside it. It counts every file under `src/`, not only the ones a test imports, and leaves out the tests themselves, their helpers and the generated `apiSchema.ts`, `generatedApi.ts` and `requestBodies.ts`. It fails when the tests cover less than 94% of lines, 87% of branches, 93% of statements or 91% of functions, the thresholds in `vite.config.js`. They sit just under the coverage when they were set (94.6%, 87.7%, 93.8% and 92.1%), which leaves about 7 lines, 5 branches, 10 statements and 4 functions of slack: one new component with a few untested handlers fails it, and a small untested change can use up the slack and leave the failure to the next one. The frontend CI runs it this way, so a drop fails the pull request. Raise them when coverage rises; lower them only on purpose, in a change that says why. Plain `npm test` skips coverage, so it stays quick while you work. In CI the `frontend` job does the same with the `frontend-coverage` artifact and the frontend badge.

### Coverage in CI

The badges in the README show the share of lines covered on `main`. The `build` and `frontend` jobs turn their report into a [shields.io endpoint](https://shields.io/badges/endpoint-badge) file (`.github/scripts/coverage.py`), and on pushes to `main` keep it as an artifact. Once a CI workflow passes on `main`, the **Coverage badges** workflow commits that file to the `badges` branch, which holds nothing else (`.github/scripts/publish-badge.sh`). It leaves the badge alone if `main` has moved on since, because the newer commit's run will publish its own if it passes. It is a workflow of its own, so the demo's deploy never waits on it and the token that can push never reaches a job that runs the build. Pull requests get the job summary and the artifacts but don't touch the badges.

### Image vulnerability scan

The `docker` job scans the image it built with **[Trivy](https://trivy.dev)**, after the end-to-end tests. It fails on a high or critical vulnerability with a fix available, in Alpine's packages or in a library in the jar, with an error pointing here. Every finding, any severity and the accepted ones too, goes under the repository's Security tab (the `security-results` job uploads them). Pull requests from forks get the scan but can't upload to the Security tab. `.trivyignore` lists the vulnerabilities the build accepts, each with why, such as ones only fixed in a major version the app isn't on yet.

A vulnerability can be published against a library at any time, so the scan can start failing on a pull request that changed nothing near it, and on `main`, where it also holds back the demo's deploy and the backend coverage badge until it passes. The fix then goes in a pull request of its own: move the library to a fixed version, through the Spring Boot version or with a version pin ahead of its BOM in `build.gradle`'s `ext` block. Add to `.trivyignore` only what can't be fixed yet, with the reason and the issue that will fix it.

To run the same scan on an image built locally (the named volume keeps Trivy's database, about 3 GB, between runs):

```bash
docker compose --profile app build app
docker save "$(docker compose --profile app config --format json | jq -r .name)-app" -o /tmp/image.tar
docker run --rm -v /tmp/image.tar:/image.tar:ro -v trivy-cache:/root/.cache/trivy \
  -v "$PWD/.trivyignore:/trivyignore:ro" "$(sed -n 's/^FROM //p' .github/trivy/Dockerfile)" \
  image --input /image.tar --scanners vuln --disable-telemetry --ignorefile /trivyignore --severity HIGH,CRITICAL --ignore-unfixed
```

The Trivy image is pinned by digest in `.github/trivy/Dockerfile`, which Dependabot updates.

### Running app scan

After the end-to-end tests, the `docker` job runs **[ZAP](https://www.zaproxy.org)**'s baseline scan against the app it started, from inside the Compose network. ZAP crawls what the app shell links to, which is little for a single-page app, so it also requests the routes open without a session that serve a page or answer a GET: sign-in, the share-link and account-link routes with made-up tokens, the API's 401s, health, the API docs. It checks every response with its passive rules: security headers, cookie flags, information leaks, caching. It doesn't attack anything or sign in, so it sees what a visitor who isn't signed in sees. The whole scan takes well under a minute.

The scan is an automation plan, `.github/zap/baseline.yaml`, run by `.github/scripts/zap-scan.sh`. Any alert fails the build, listed as `ALERT` lines with an error pointing here, unless the plan's alert filters accept it. Each accepted one says why, is scoped to where that reason holds (one cookie, one kind of URL), and the ones waiting on a fix link to its issue. Fix what it finds where you can. Accept an alert only when it's expected for this app, with the reason. The `zap-results` artifact holds the HTML report for 14 days, and every alert goes under the Security tab with the category `zap`, the accepted ones at the lowest level. Code scanning only takes locations in the repository, so each alert is filed under its URL's path, such as `api/me` or `assets/index.js`, with the full URL at the top of its message.

ZAP runs from the image pinned by digest in `.github/zap/Dockerfile`, which Dependabot updates, with `-silent`, so it makes no update checks of its own. The image only has ZAP's release passive rules. Its beta ones check the Permissions-Policy, cross-origin and caching headers, so the script adds them, pinned by URL and hash in `.github/zap/addons.txt`. The plan names three of their rules, so if the add-on ever doesn't load, ZAP warns and the scan fails rather than passing without them. So does any other warning about the plan. When Dependabot moves ZAP to a new version, take the add-on's newest URL and hash for that version from ZAP's add-on list, as that file says. A new version can bring new or stricter rules that fail the build; fix or accept what they find in the same pull request.

To run the same scan locally, start the stack and finish first-run setup, as the end-to-end tests do in CI. Until then every route sends the browser to `/setup`, so the scan sees almost nothing:

```bash
docker compose --profile app up --build --wait
# Finish setup at http://localhost:8080 with the code from the app's log, or run npm run e2e.
.github/scripts/zap-scan.sh /tmp/zap
docker compose --profile app down --volumes
```

The report is then `/tmp/zap/zap.html`.

### End-to-End Tests

The backend and frontend suites each mock the other side, so a mismatch between them (an endpoint path, a CSRF header, a response shape) passes both. The **Playwright** tests in `e2e/` close that gap: they drive the real app in Chromium against the Docker Compose stack, the same image, PostgreSQL database and storage volume a user runs.

```bash
# Start a fresh stack: setup only happens once, on an empty database
docker compose --profile app down --volumes
docker compose --profile app up --build --wait

# Once: the test dependencies and the browser
npm install --prefix e2e
npx --prefix e2e playwright install chromium

# Run the suite, then open the report (with a trace of any failure)
npm run e2e
npm run report --prefix e2e
```

The `setup` project runs first. On a fresh stack it reads the setup code from `docker compose logs app`, as the README tells a user to, creates the account and signs in; on a stack already set up it only signs in. Every other test starts from that signed-in session, in a folder of its own created through the API, so the tests run in parallel and can run again on the same stack. Arguments after `--` go to Playwright, such as `npm run e2e -- --headed` or `npm run e2e -- tests/share.spec.js`.

| Variable | Default | Use |
|----------|---------|-----|
| `E2E_BASE_URL` | `http://localhost:8080` | Where the app is running |
| `E2E_USERNAME`, `E2E_PASSWORD` | A fixed test account | The account setup creates, or the one to sign in with on a stack set up by hand |
| `E2E_SETUP_CODE` | Read from the container log | The setup code for a server Docker Compose did not start, such as `./gradlew bootRun` with `app.setup.code` set |

Docker Compose's own `COMPOSE_PROJECT_NAME` and `COMPOSE_FILE` are honoured when reading the log, for a stack started under another name or with an override file.

The `docker` job runs the suite twice: on the stack as above, then on the same image with search on Elasticsearch, started as [self-hosting.md](self-hosting.md#lucene-or-elasticsearch) sets it up (`COMPOSE_PROFILES=app,elasticsearch` and `JAVADROPBOX_SEARCH_BACKEND=elasticsearch`), after checking the app's log says it uses it. To run it that way locally, start the stack with those two variables set, and stop it with `docker compose --profile app --profile elasticsearch down --volumes`.

CI runs the suite in the `docker` job of `.github/workflows/gradle.yml` after the stack is up, and uploads the HTML report as the `playwright-report` artifact when a test fails.
